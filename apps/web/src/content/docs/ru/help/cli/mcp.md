`copalibre mcp` запускает локальный сервер [Model Context Protocol](https://modelcontextprotocol.io)
только через stdio — без транспорта HTTP/SSE. Клиент MCP (например, ИИ-агент) запускает процесс и
взаимодействует через его стандартный ввод/вывод; сообщения журнала (баннер и т. д.) идут через
stderr, никогда не смешиваясь с протоколом.

## Инструменты установки

Всегда доступны, без необходимости настройки токена — они выполняют ту же логику, что и
соответствующие команды CLI, в том же процессе:

- **`copalibre_doctor`**: проверяет конфигурацию и зависимости (как `copalibre doctor`).
- **`copalibre_module_list`**: перечисляет установленные модули.
- **`copalibre_upgrade_check`**: проверяет совместимость модулей и ожидающие миграции против
  целевой версии (`target_version`), как `copalibre upgrade-check`.

## Инструменты создания модулей

Всегда доступны, без токена — они работают с локальной файловой системой и Git, никогда с
`apps/api`:

- **`copalibre_module_scaffold`**: генерирует структурно корректный пакет модуля, основанный на уже
  корректном документе каталога, в виде помеченного локального Git-репозитория.
- **`copalibre_module_validate_local`**: проверяет локальный пакет без его поиска или установки.
- **`copalibre_module_submit`**: форкает `copalibre-modules`, публикует модуль в новой ветке и
  открывает pull request.

Это полный сценарий, оправдывающий существование этого сервера: ИИ читает правила вида спорта,
спрашивает у оператора необходимые детали, собирает модуль локально, проверяет его, устанавливает в
локальную установку для разработки, чтобы действительно опробовать его (через `copalibre module add
--source file://...`, без отдельного механизма), и отправляет его как pull request — всё это, не
покидая протокол MCP.

## Инструменты управления турнирами

Регистрируются только когда настроены `COPALIBRE_MCP_TOKEN` и `COPALIBRE_API_URL` — без токена они
даже не появляются в списке инструментов сервера, и никакой HTTP-вызов никогда не предпринимается.
`COPALIBRE_MCP_TOKEN` — это уже действительный bearer-токен по тому же контракту аутентификации
OIDC/JWT, который использует остальная часть API; эта команда не выдаёт и не управляет токенами, а
только пересылает их.

- **`copalibre_get_organization`**: читает организацию по её алиасу.
- **`copalibre_list_tournaments`**: перечисляет активные (неархивированные) турниры организации.
- **`copalibre_get_tournament`**: читает турнир по его алиасу внутри организации.
- **`copalibre_create_tournament`**: создаёт турнир в состоянии черновика.
- **`copalibre_publish_tournament`**: публикует конфигурацию турнира-черновика.

Это начальный, отобранный набор, а не исчерпывающее зеркало каждой конечной точки `apps/api` —
расширение его позже является ожидаемой работой, а не фиксированным пределом.

## Настройка клиента MCP

Типичный клиент MCP запускает `copalibre mcp` как подпроцесс, передавая необходимые переменные
окружения (`DATABASE_URL` и, опционально, `COPALIBRE_MCP_TOKEN`/`COPALIBRE_API_URL` для
инструментов турниров). Смотрите
[`docs/MCP.md`](https://github.com/SebaSOFT/copalibre/blob/develop/docs/MCP.md) в репозитории для
полного примера конфигурации.

## Документация для ИИ

Сервер MCP объявляет свои собственные `instructions` в ответе `initialize` — то же резюме, что и на
этой странице, в форме, которую клиент MCP читает перед выбором инструмента. Тот же экземпляр также
публикует `/llms.txt` и `/llms-full.txt` в корне сайта справки, для ИИ, который вместо этого
обходит отрендеренные страницы.

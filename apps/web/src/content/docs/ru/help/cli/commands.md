Каждая команда отвечает на `--help`/`-h` именно этим текстом использования, сгенерированным из
единого источника внутри самого CLI — эта страница не может описывать команду иначе, чем CLI
действительно работает. `copalibre --version` выводит только установленную версию, для скриптов.

## init

`copalibre init [--module-dev]` или `copalibre init --kubernetes [--namespace <ns>] [--release
<имя>] [--context <ctx>]`

Записывает полную установку в текущий каталог. Не требует checkout исходного кода: запустите её в
любом пустом каталоге, и каждая последующая команда автоматически определяет этот каталог по
маркеру (`.copalibre/installation.json`), который она записывает, — так же, как `.git` отмечает
checkout репозитория. Отказывается выполняться повторно в каталоге, где уже есть установка. Каталог
остаётся закреплён за версией CopaLibre, с которой его создал `init` — запуск нескольких версий
параллельно означает запуск соответствующей версии CLI для каждого каталога (см.
[обновление](/ru/help/cli/updating/)).

Без `--kubernetes` записывает `docker-compose.yml` и `.env` с несекретными значениями по умолчанию
и перечисляет необходимые секреты для заполнения в `.env` после.

- `--module-dev`: также записывает `docker-compose.module-dev.yml` и каталог `modules-dev/`,
  примонтированный в `api`/`worker` с предустановленным `COPALIBRE_MODULE_SOURCE_ALLOWLIST` —
  сочетается с `module scaffold --output modules-dev/<alias>` и `module add <alias> --source
file:///var/lib/copalibre/modules-dev/<alias>` для разработки модуля против работающего
  самостоятельно размещённого экземпляра без checkout исходного кода.

С `--kubernetes` вместо этого записывает заготовку Helm `values.yaml` — без файла compose, без
`.env`; собственный механизм Secret/ConfigMap Kubernetes остаётся авторитетным для конфигурации.
Полный процесс, включая bootstrap первого администратора как одноразового Helm Job:
`docs/deployment/enterprise-kubernetes.md` в репозитории.

- `--kubernetes`: создаёт заготовку установки Helm вместо Compose
- `--namespace <ns>`: пространство имён Kubernetes для записи (по умолчанию: `default`)
- `--release <имя>`: имя релиза Helm для записи (по умолчанию: `copalibre`)
- `--context <ctx>`: kube-context для записи (по умолчанию: нет — передавайте явно каждый раз)

## doctor

`copalibre doctor [--check-proxy] [--proxy-url <url>]`

Проверяет конфигурацию и зависимости перед запуском.

- `--check-proxy`: дополнительно проверяет конфигурацию обратного прокси
- `--proxy-url <url>`: публичный URL для проверки при использовании `--check-proxy`

## dev

`copalibre dev [--hybrid]`

Запускает среду разработки, контейнеризованную или гибридную.

- `--hybrid`: инфраструктура в Docker, процессы приложения на хосте

## start

`copalibre start`

Поднимает PostgreSQL, запускает doctor и все роли процессов.

## migrate

`copalibre migrate`

Выполняет ожидающие миграции базы данных.

## backup

`copalibre backup [--file <путь>] [--retain <n>] [--dry-run]`

Создаёт сжатый **пакет резервной копии** (`.tar.gz`) в `backups/`, с дампом PostgreSQL и
манифестом (дата и версия CopaLibre). Применяет удержание: после успешной резервной копии удаляет
более старые пакеты сверх `--retain`. Удаляет только файлы, соответствующие шаблону имени пакета
(`copalibre-<дата>.tar.gz`) — никогда не трогает другие файлы в `backups/`.

- `--file <путь>`: назначение пакета внутри `backups/` (по умолчанию: имя с временной меткой)
- `--retain <n>`: пакеты для сохранения после этой резервной копии (по умолчанию: 5)
- `--dry-run`: выводит план резервного копирования, не выполняя его

Данные установленных модулей (дескрипторы дисциплин, профили турниров) находятся в PostgreSQL,
поэтому включены в дамп. Байты объектов в объектном хранилище (`object-storage-data`) вне области
действия этой команды — создавайте их резервные копии отдельно на уровне инфраструктуры, как уже
указано в руководстве по самостоятельному размещению.

## restore

`copalibre restore --file <путь> (--confirm | --dry-run) [--allow-newer-backup]`

Извлекает пакет резервной копии, восстанавливает его дамп PostgreSQL, выполняет ожидающие миграции
и подтверждает, что применённая схема соответствует этой установке — всё за один вызов.

- `--file <путь>`: пакет для восстановления, внутри `backups/`
- `--confirm`: требуется для фактического выполнения восстановления
- `--dry-run`: выводит план восстановления, не выполняя его
- `--allow-newer-backup`: разрешает восстановление пакета, созданного более новой версией CopaLibre,
  чем текущая запущенная (по умолчанию отклоняется)

После успешного `pg_restore` `restore` автоматически выполняет `copalibre migrate`, а затем
открывает соединение, чтобы проверить, что версия применённой схемы точно соответствует ожидаемой
этой установкой (та же проверка, что использует `GET /ready`) — так восстановление никогда не
оставляет код и базу данных незаметно рассинхронизированными. Если миграция не удаётся, `restore`
сообщает об этом своим кодом выхода, не заявляя об успехе; повторите попытку с `copalibre migrate`,
а затем `copalibre doctor`.

Пакет, чей манифест фиксирует версию CopaLibre более новую, чем текущая запущенная, отклоняется до
обращения к базе данных, с указанием обеих версий — сначала обновите эту установку, либо передайте
`--allow-newer-backup`, если вы действительно намерены продолжить.

## upgrade-check

`copalibre upgrade-check --target-version <semver>`

Проверяет совместимость установленных модулей и ожидающие миграции перед обновлением.

- `--target-version <semver>`: версия CopaLibre, против которой проверяются модули и миграции

Завершается с ненулевым кодом выхода, если какой-либо установленный модуль перестанет быть
совместимым с целевой версией. Смотрите [обновление](/ru/help/cli/updating/) для полной
последовательности.

## create-admin

`copalibre create-admin --organization-alias <alias> --organization-name <название> --email <email>`

Создаёт первую учётную запись администратора организации.

## login

`copalibre login [--api-url <url>] [--token <token>]`

Сохраняет персональный токен доступа, чтобы `statistics-rebuild` и `module add/list/remove/verify`
могли работать с удалённой установкой через аутентифицированное HTTP-соединение — способ
администрировать уже работающую установку, включая установку или обновление CLI после того, как
Docker уже запущен, с машины, которой никогда не нужны учётные данные базы данных. Создайте токен на
экране настроек панели управления, уже находясь в системе, затем вставьте его сюда. Проверяет токен
одним аутентифицированным вызовом перед сохранением; отказывает и ничего не сохраняет, если токен
недействителен.

- `--api-url <url>`: целевая установка (по умолчанию: `COPALIBRE_API_URL`, которую `copalibre init`
  уже записывает в `.env`)
- `--token <token>`: сам токен (по умолчанию: считывается из stdin при передаче через pipe, либо
  через интерактивный запрос, маскирующий каждое нажатие клавиши)

Сохраняет учётные данные в `.copalibre/credentials.json` (`0600`) текущего каталога — запускайте
`login` изнутри каталога установки, созданного `copalibre init`. Повторный запуск `login` в том же
каталоге заменяет сохранённый токен, в отличие от маркера `init`.

## statistics-rebuild

`copalibre statistics-rebuild --organization <alias> [--tournament <alias>]`

Пересчитывает каждый свёрнутый статистический итог (`statistic_totals`) на основе исходных фактов —
зарегистрированных событий завершённых матчей, составов и ручных корректировок — по умолчанию для
всей организации либо ограниченно для одного турнира.

- `--organization <alias>`: организация, для которой пересчитываются статистика
- `--tournament <alias>`: ограничивает пересчёт одним турниром внутри организации

Идемпотентна: использует тот же путь `refold` и запись через удаление-затем-вставку, что и триггер,
управляемый событиями, поэтому запуск дважды подряд даёт побайтово идентичные строки
`statistic_totals` (кроме `updated_at`/внутренней версии проекции). Полезна для восполнения истории,
зафиксированной до появления движка свёртки, или для проверки итогов против фактов в любой момент.
Требует прав администратора организации после входа через [`login`](#login).

## module

`copalibre module <add|list|remove|verify>`

Управляет установленными модулями дисциплин и профилей турниров. `add`/`list`/`remove`/`verify`
требуют прав супер-администратора установки после входа через [`login`](#login).

### module add

`copalibre module add <alias>[@диапазон] [--source <url>] [--allow-unsatisfied-capabilities]`

Устанавливает модуль по алиасу, опционально закреплённый на диапазоне версий.

- `--source <url>`: явно включённый альтернативный источник вместо отобранного
- `--allow-unsatisfied-capabilities`: устанавливает, даже если заявленные необходимые возможности
  ещё не удовлетворены

### module list

`copalibre module list [--outdated]`

Перечисляет установленные модули или только те, у которых есть более новая опубликованная версия.

- `--outdated`: показывает только модули с более новой опубликованной версией

### module remove

`copalibre module remove <alias>`

Удаляет установленный модуль, на который не ссылается ни один начатый турнир.

### module verify

`copalibre module verify`

Повторно проверяет каждый установленный модуль против запущенной версии ядра.

### module scaffold

`copalibre module scaffold <discipline|tournament-profile> <alias> [--author <автор>] [--licence <лицензия>] [--name <название>] [--source-url <url>] [--output <каталог>]`

Генерирует структурно корректный пакет модуля для начала разработки — основанный на одном из уже
корректных документов каталога CopaLibre, а не на слепом угадывании схемы — в виде помеченного
локального Git-репозитория, готового к редактированию, проверке и установке/отправке.

- `--author <автор>`: автор атрибуции (по умолчанию: Unknown)
- `--licence <лицензия>`: идентификатор SPDX (по умолчанию: AGPL-3.0-only)
- `--name <название>`: имя развёртывания (по умолчанию: алиас)
- `--source-url <url>`: исходный URL атрибуции
- `--output <каталог>`: куда записать репозиторий модуля (по умолчанию: `modules/<alias>`)

### module validate-local

`copalibre module validate-local <путь>`

Проверяет локальный пакет модуля без его поиска или установки — та же проверка, которую уже
применяют `module add`/`module verify`.

### module submit

`copalibre module submit <путь> [--upstream <owner/repo>] [--base <ветка>]`

Форкает `copalibre-modules`, копирует локальный модуль в новую ветку, публикует её и открывает
pull request.

- `--upstream <owner/repo>`: целевой репозиторий (по умолчанию: `SebaSOFT/copalibre-modules`)
- `--base <ветка>`: базовая ветка pull request (по умолчанию: `main`)

## mcp

`copalibre mcp`

Запускает локальный сервер Model Context Protocol (MCP) через stdio, чтобы ИИ мог управлять
CopaLibre. Смотрите [подробности об инструментах MCP](/ru/help/cli/mcp/).

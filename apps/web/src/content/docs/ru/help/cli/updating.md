## Обновление самого CLI copalibre

`copalibre --version` выводит версию установленного бинарного файла. Повторный запуск скрипта
установки загружает последний опубликованный релиз и заменяет бинарный файл на месте — это
идемпотентно: сначала проверяется установленная версия, и загрузка пропускается, если она уже
совпадает:

```bash
curl -fsSL https://github.com/SebaSOFT/copalibre/releases/latest/download/install.sh | bash
```

Это заменяет только бинарный файл `copalibre`. Это не влияет на работающую установку — см. ниже об
обновлении фреймворка и его модулей.

## Обновление фреймворка

Запустите `copalibre upgrade` в каталоге установки с CLI той версии, на которую переходите. Сначала
посмотрите, что он сделает; это ничего не меняет:

```bash
copalibre upgrade --check
```

### С какой версии вы начинаете

| Установку создала версия                        | Что делать                                                                                            |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| 1.2.5 или 1.2.6                                 | `copalibre upgrade --self`, затем `copalibre upgrade --check` и `copalibre upgrade`                   |
| 1.2.1 или более ранняя (в её CLI нет `upgrade`) | Установите новый CLI скриптом установки выше, затем `copalibre upgrade --check` и `copalibre upgrade` |
| CLI 1.2.x уже выполнил `copalibre upgrade`      | Установите новый CLI и выполните `copalibre upgrade` ещё раз                                          |

Не давайте CLI 1.2.x выполнять `copalibre upgrade` самостоятельно. Он записывает новую версию в
`.env`, `docker-compose.yml` и `.copalibre/installation.json`, сообщает об успехе и оставляет все
контейнеры на старых образах; при следующем перезапуске новые образы стартуют со старым файлом
Compose, и это не работает. Новый CLI распознаёт оставленную так установку, что бы ни говорил её
маркер, и доводит дело до конца.

### Что делает обновление

1. Загружает новые образы, пока установка продолжает работать, чтобы ничего не остановилось, если
   какого-то образа нет.
2. Останавливает стек, чтобы не потерять ни одной записи, и сохраняет резервную копию базы в
   `backups/pre-upgrade-<с>-to-<на>-<дата>.tar.gz`.
3. Заменяет `docker-compose.yml` и `deploy/gateway/Caddyfile` файлами новой версии, если они остались
   такими, какими их поставила одна из версий, и сохраняет прежние как `docker-compose.yml.<с>.bak` и
   `deploy/gateway/Caddyfile.<с>.bak`. Обновляет `.env` (новые параметры, новые теги образов, адрес
   набора ключей, перенесённый под `/api`) и сохраняет `.env.<с>.bak`; заданные вами значения
   остаются.
4. Переносит базу с PostgreSQL 17 на 18: восстанавливает резервную копию в новый том
   (`postgresql-data`) и сравнивает число строк в каждой таблице, прежде чем продолжить. Том 17 не
   затрагивается.
5. Запускает новую версию и выполняет `copalibre doctor`.
6. Когда doctor проходит, проверяет, что резервную копию можно прочитать, и затем удаляет том
   PostgreSQL 17 (`postgres-data`) и образ `postgres:17`. С `--keep-old-volume` они сохраняются;
   обновление выводит две команды, которыми их можно удалить позже.

Стек остановлен с шага 2 до успешного завершения шага 5; планируйте окно по размеру базы. Для
переноса нужно свободное место под вторую копию базы: без него обновление не начнётся. После
обновления скопируйте пакет резервной копии за пределы сервера.

### Если вы изменяли docker-compose.yml

Файл Compose, не совпадающий ни с одной версией (добавленный сервис, изменённое значение),
остаётся как есть. Обновление записывает файл новой версии как `docker-compose.yml.new`, сообщает об
этом и останавливается, ничего больше не меняя. Перенесите свои изменения в этот файл, замените
`docker-compose.yml` результатом и снова выполните `copalibre upgrade`. Изменённая вами конфигурация
gateway сохраняется, и обновление об этом сообщает.

### Установки версии 1.0

В 1.0 не было gateway: пограничный прокси обращался к `web`, `api` и `events` напрямую. Начиная с
1.1 единственная точка входа — сервис `gateway` на `COPALIBRE_PORT` (8080, если не задано). После
обновления направьте прокси на gateway и задайте в `COPALIBRE_APP_URL` адрес, которым пользуются
браузеры; проверьте это командой `copalibre doctor`.

### Откат

Если любой шаг до doctor завершается ошибкой, обновление возвращает прежние файлы, запускает прежнюю
версию на нетронутом томе PostgreSQL 17 и сообщает, почему остановилось. Если не проходит doctor,
новая версия продолжает работать, а обновление выводит эти шаги, ничего не удаляя.

Пока том PostgreSQL 17 существует (doctor не прошёл или вы указали `--keep-old-volume`):

```bash
docker compose down
cp docker-compose.yml.<с>.bak docker-compose.yml
cp .env.<с>.bak .env
cp deploy/gateway/Caddyfile.<с>.bak deploy/gateway/Caddyfile   # если обновление его заменило
docker compose up --detach --wait
```

Том PostgreSQL 18 (`<проект>_postgresql-data`) остаётся неиспользуемым; удалите его командой
`docker volume rm` перед повторной попыткой обновления, если хотите начать с чистого листа.

После того как обновление удалило PostgreSQL 17, путь назад — пакет резервной копии. Установите CLI
прежней версии в новый пустой каталог, выполните там `copalibre init`, скопируйте пакет в его
`backups/` и восстановите его:

```bash
copalibre restore --file backups/pre-upgrade-<с>-to-<на>-<дата>.tar.gz --confirm
```

Записи, сделанные после обновления, теряются. Запуск прежних образов поверх уже перенесённой базы
никогда не является безопасным откатом.

### Ручное обновление через Compose (между версиями 2.x)

С установки 1.x используйте `copalibre upgrade`: её база должна перейти на PostgreSQL 18, а эти шаги
этого не делают.

Сохраните CLI, соответствующий `.copalibre/installation.json`. Замена бинарного файла не обновляет маркер, Compose и версии образов. Сохраните резервные копии PostgreSQL, объектов, конфигурации и ключей подписи, а также прежние версии образов.

```bash
copalibre backup --file backups/pre-upgrade.tar.gz
```

В существующем каталоге установки проверьте изменения Compose и конфигурации целевой версии, затем измените оба образа в `.env`. Сохраните проект Compose и тома. Загрузите и проверьте целевой образ без запуска зависимостей и применения миграций:

```dotenv
COPALIBRE_IMAGE=ghcr.io/sebasoft/copalibre:1.2.6
COPALIBRE_WEB_IMAGE=ghcr.io/sebasoft/copalibre-web:1.2.6
```

```bash
docker compose pull
docker compose run --rm --no-deps upgrade-check --target-version 1.2.6
```

После успешной проверки запланируйте перерыв, остановите процессы приложения и создайте окончательную резервную копию; затем выполните миграцию и запуск. Не запускайте приложение при ошибке миграции:

```bash
docker compose stop gateway web web-ssr api events worker scheduler
copalibre backup --file backups/pre-upgrade.tar.gz
docker compose run --rm migrate && docker compose up --detach --wait
docker compose run --rm doctor
```

Не удаляйте и не переписывайте маркер для обхода проверки версии. Для операций со схемой между версиями используйте указанные сервисы Compose: новый CLI откажет в `migrate` и `upgrade-check` со старым маркером. Новый каталог `init` — отдельная установка, а не обновление существующей.

После миграции базы выбор старых образов не является безопасным откатом. Оставьте процессы записи остановленными и восстановите PostgreSQL, объекты и конфигурацию в изолированной установке прежней версии. Проверьте восстановление до переключения трафика; записи после резервной копии будут потеряны.

## Обновление по типу развёртывания

Для Compose за NGINX или Caddy сохраните прокси и сертификаты, включите обслуживание на время миграции и проверяйте/перезагружайте только изменённую конфигурацию. В Kubernetes используйте целевой chart с проверенными значениями и обоими образами, сначала запустите Job проверки совместимости, затем проверьте Job миграции/doctor и ingress до открытия трафика. Helm rollback не отменяет миграции базы. Подробные команды:

- [Caddy](https://github.com/SebaSOFT/copalibre/blob/main/docs/deployment/reverse-proxy/caddy.md#upgrading-copalibre-behind-caddy)
- [NGINX](https://github.com/SebaSOFT/copalibre/blob/main/docs/deployment/reverse-proxy/nginx.md#upgrading-copalibre-behind-nginx)
- [Kubernetes / Helm](https://github.com/SebaSOFT/copalibre/blob/main/docs/deployment/enterprise-kubernetes.md#upgrading-an-existing-helm-release-safely)

## Обновление модулей

Каждая установленная дисциплина или профиль турнира — это модуль, версионируемый независимо от
фреймворка.

```bash
copalibre module list --outdated
```

Показывает только установленные модули, у которых опубликованная версия новее установленной.

```bash
copalibre module add <alias>@<диапазон>
```

Устанавливает конкретную версию или диапазон (например, `@^2.0.0`) уже установленного модуля —
переустановка с другой версией является способом обновления модуля. Уже начатый турнир продолжает
ссылаться на версию, с которой он был создан; обновление модуля никогда не изменяет задним числом
уже идущий турнир.

Смотрите [справочник команд](/ru/help/cli/commands/) для остальных опций `module`.
